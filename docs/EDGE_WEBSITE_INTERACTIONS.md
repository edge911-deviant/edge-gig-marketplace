# EDGE public website interactions

The website introduces EDGE as a structured network for live performance: artists find work, organisers produce events, venues host and programme shows, and audiences discover artists and local live moments. Motion supports that explanation and the next action. The public POC must never look like a live booking or ticketing service that is already complete.

## Interaction contract

- `Keep it clear.` replays on tap/click or keyboard focus, and gives one brief introductory pulse. No rapidly flashing background or duplicated accessible text.
- The hero is one console with three mutually exclusive modes: Your role, Brief → show, and Nearby. Frame-anchored traces acknowledge real selection changes. There are no rotating cubes, continuous decorative geometry, or invented marketplace metrics. The existing generated stage image stays prominent.
- Your role contains four perimeter buttons and a brief actionable explanation below the image. Its selection is shared with the lower role circuit. Each role links to its real website section.
- Brief → show has four selectable steps: brief, artist, booking, show. Play/Pause/Replay is bounded to one pass and stops offscreen, when the tab is hidden, when switching modes, and when visual effects are paused. The brief opens an actual demo detail dialog. Public show publishing is explicitly described as planned, not already live.
- Nearby displays the actual filtered demo count, dated sample records, soonest/latest order, selection details, and a useful end-of-sample link to the discovery board. PIN, place, city, genre and ordering share one model with that board. Do not build a second conflicting local inventory.
- A single pointer-transparent crosshair replaces the native arrow on fine-pointer public website surfaces. A native crosshair is the fallback until the custom reticle is positioned; text fields retain an I-beam. The custom cursor is absent on coarse pointers and over dialogs/native inputs. Disabling decorative motion keeps this essential cursor visible without its enlargement effect. The authenticated app cursor is unchanged.
- Motion preference is local to the browser session. Device reduced-motion settings take precedence. Controls work even if session storage is unavailable. Motion off also disables smooth anchor scrolling.
- Artist, Organiser, Venue and Audience nodes are buttons with `aria-pressed`, updated explanatory text and links to their role sections.
- Demo PINs `700001`, `400001`, `560001` select Kolkata, Mumbai and Bengaluru respectively. City names and common aliases such as Bangalore are also accepted. Unknown/short PINs and unsupported places produce recoverable inline feedback; city shortcuts always remain available. No external location lookup occurs.
- `Use demo location` simulates Kolkata. No device location is requested, transmitted or stored.
- The nine public listings are fictional, isolated from authenticated data. Genre filters work in both discovery modes. Brief/show detail dialogs create no applications, bookings or tickets.
- PATCH is the EDGE guide. Its rendered companion is visible by default beside the hero explanation on desktop, in reserved space rather than over the performers. It greets once and responds to pointer position, keyboard focus and presses. On smaller screens, help remains accessible in navigation. Answers are curated; no AI chat or live agent is connected. The contact link opens an email draft and sends nothing automatically.
- Native dialogs provide focus handling and Escape dismissal. Preserve the named close controls and return focus to the opening control.
- Mobile rails determine their own frame height so wrapped show names never clip the replay or end-of-sample action. Controls tested in the narrow phone viewport are at least 44px high. Brief CRT acknowledgement belongs to real interactive controls; no ambient rapid flicker or endless pulsing background.

## Next implementation boundary

Real location lookup needs an actual PIN/geographic data source and permission/error handling. Public event discovery needs host-controlled publication and a safe public data projection. Help can later be backed by a support service; keep account data out of it until that integration is deliberately designed. Test these interactions on physical touch devices and with assistive technology before claiming accessibility compliance.
